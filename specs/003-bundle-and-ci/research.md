# Phase 0 — research: bundle, rules bootstrap and CI

Nothing here was marked NEEDS CLARIFICATION in the plan; the open questions were all
"which mechanism", and each is settled below with what was rejected. Verified against the
repository as it stands on `4aa0a28`, not from memory.

## D1 — `bundle` is a second template over the existing report model

**Decision**: add `render.render_bundle(model, template_dir)` and
`templates/bundle.md.j2`, fed by the same `_build_model(run_dir)` that `cmd_report` uses.
`bundle` writes `<run_dir>/bundle.md` and prints the path; `--json` emits the usual
`{"schema": "ens-evidence/1", ...}` line.

**Rationale**: the model already carries everything the bundle needs — top findings by
severity, measures, coverage, counts including `unmapped`, run metadata — and it already
routes every piece of scanned-repo text through `render.fence()` (`render.py:55`), the single
truncating, delimiting, fence-defanging path. A second renderer over the same model inherits
that guarantee; a bespoke assembler would re-open the injection surface the fixture exists to
close.

**Alternatives rejected**:
- *Bundle as a post-processed subset of `report.md`* — string-slicing a rendered document to
  keep "the top part" is exactly how a disclaimer gets dropped (Principle II, IV).
- *`bundle` re-scans* — breaks Principle I and duplicates `scan`; the run store is the source.
- *Emit to stdout instead of a file* — stdout is reserved for machine JSON
  (`DESIGN.md`: machine output to stdout, human chatter to stderr). Writing beside `report.md`
  keeps the run directory the single self-contained evidence unit, which is also what the
  self-scan artifact uploads.

## D2 — `rules fetch` is a pinned depth-1 git fetch, gated on an explicit acknowledgement

**Decision**: `ens-evidence rules fetch --sha <commit> [--repo URL] --accept-rules-license`
creates `.ens-rules/`, then `git init` → `git remote add origin <url>` →
`git fetch --depth 1 origin <sha>` → `git checkout FETCH_HEAD`, invoked as subprocesses.
Without `--accept-rules-license` (or `ENS_EVIDENCE_ACCEPT_RULES_LICENSE=1`) it prints our own
summary of the licence terms plus the upstream URL and exits 2 having fetched nothing.
`rules status` prints the existing `rules_info(cfg)` — mode, repo, SHA, per-language rule
counts — as one JSON line.

**Rationale**: `--depth 1` on an explicit SHA is the only fetch shape that is both pinned and
cheap; `git clone --branch` cannot take an arbitrary commit. `git` is already a subprocess
dependency (`run.py:_git`), so this adds no Python dependency and matches the
engines-are-subprocesses constraint. `rules_info()` and `rules_per_language()` already exist and
are already recorded into `run.json` — `status` is a printer, not new logic.

**Alternatives rejected**:
- *Full clone then checkout* — downloads the entire rule history into a CI runner for one SHA.
- *Tarball download from the forge API* — an unauthenticated, rate-limited network path with no
  commit verification, and it drifts if the forge changes URL shapes.
- *GitPython* — a dependency for something three subprocess calls do.
- *Implicit acknowledgement via config file* — the licence gate must be an act, not a default.
  A `.ens-evidence.yml` key would be copied between repos unread.
- *Our own wording of the licence* only. We link and summarise; we do not vendor the licence
  text (Principle V's spirit: no bulk third-party text).

## D3 — the injection proof runs engine-free, from a committed stored run

**Decision**: `tests/fixtures/injection-app/` gets real hostile content across the three
surfaces that reach a document — code comments, file paths, and dependency metadata (a lockfile
with an injected package description). A stored run of it is committed at
`tests/fixtures/run-injection/`, generated by the procedure in
`tests/fixtures/run/README.md`. `test_injection.py` renders the bundle from that stored run and
asserts, for every injection string in a checked-in list, that it appears only inside a fenced
block and never as document text.

**Rationale**: the existing test job runs `pytest -m "not engines"` and must stay green with no
Semgrep and no Trivy installed. An injection proof that only runs where the engines exist is a
proof that does not run. The stored-run fixture pattern is already established and documented,
including the two traps: Semgrep scans only git-tracked files, and its defaults skip anything
under `tests/`, so the fixture must be scanned from a separate work tree.

**Alternatives rejected**:
- *Assert on `fence()` in isolation* — a unit test on the helper proves nothing about whether
  the template actually routes every field through it. The defect class here is a template that
  forgets the filter on one field.
- *Live scan in the test* — engine-dependent, non-deterministic across rule updates.
- *Injection strings inline in the test only* — they must exist in a scanned repository, or the
  test never exercises the normalise → map → render path where a field can escape the fence.

**Explicitly in scope for the fixture, because a human reader and an agent see different
things**: zero-width and bidirectional control characters, and a string containing the fence
delimiter itself (`fence()` already rewrites ``` to ''' — the test pins that behaviour).

## D4 — one tracked pin file drives both workflows

**Decision**: the pinned rules SHA lives in `.github/semgrep-rules.sha` (one line, a commit
SHA). `scan.yml` reads it and passes it to `rules fetch`. A `rules-bump` job in `ci.yaml`
runs when that file changes in a pull request: it fetches the new rules, scans the committed
fixture corpus, and pipes each run's `findings.jsonl` through `scripts/unmapped_ids.py`, which
exits 1 listing every rule id filed as `unmapped`.

**Rationale**: constitution 1.4.0 requires rules-SHA bumps to go through the fixture loop with
new unmapped ids mapped before the bump merges. A gate needs a trigger, and a trigger needs a
single file to watch — today the SHA exists only in a comment in the stub workflow. The
unmapped signal already exists in the data: the mapper files unmapped findings as
`measures == ["unmapped"]` (`mapper.py:62`), so the check is a filter over `findings.jsonl`, not
new analysis.

**Alternatives rejected**:
- *`python -c` inline in the workflow YAML* — cannot be unit-tested and cannot be run locally
  before pushing, which is how the current `scan.yml` stub survived unverified.
- *Gate on the report's unmapped appendix* — requires rendering, and couples a CI gate to a
  presentation artifact.
- *Run the loop on every push* — pointless network and engine time; the gate is about the bump.
- *Fail the self-scan on the repository's own findings* — couples every unrelated pull request
  to upstream rule drift. The self-scan reports; the bump job gates (spec Assumptions).

## D6 — two controls, because a path cannot be fenced (found during implementation)

**Decision**: add `render.inline_untrusted()` — flatten, mark Unicode `Cc`/`Cf` characters,
replace the backtick and the pipe, truncate to 120 characters — and apply it to every inline
repository-controlled field (`file`, `rule`, `tool`, language names) in **both** templates. The
bundle states before its first table that such values are data, not instructions.

**Rationale**: FR-003 as originally written ("everything through `fence()`") is
unimplementable. A finding's location must be shown, and a table cell or bullet cannot hold a
fenced block. Building the fixture also showed the shipped 002 report was exposed: a path
containing a backtick closed its code span, and a pipe broke its cell, so the rest of the
attacker-chosen path became document prose. That is a security defect in merged code, in the
exact class this feature exists to close, so it is fixed here rather than filed.

**Also learned, and now in the spec**: the repository-controlled fields that actually reach a
document are the path, the stored snippet and (in pinned mode) the path-derived rule id —
engine messages are the rules' text, not the repository's. And a hostile value only proves
something if it is attached to a finding the document renders: the bundle shows the top
severities only, so the first fixture attempt put the hostile path on a low-severity finding
that never appeared, and the test passed while proving nothing.

**Alternatives rejected**:
- *Fence the paths too* — destroys every table in both documents.
- *Omit hostile-looking paths* — a finding without its location is not evidence.
- *Escape only the backtick* — the pipe breaks the cell on its own, and control characters hide
  a directive from the human reviewer while the model still reads it.

## D5 — the licence boundary is enforced by a step, not by review

**Decision**: `scan.yml` uploads `out/latest/` by explicit path, and immediately before the
upload a step fails the job if the staged directory contains any file under a `.ens-rules`
path or any `*.yaml`/`*.yml` file originating from the rules root. No cache is keyed on rule
file contents, and `.ens-rules/` stays in `.gitignore` and in `run.py:SKIP_DIRS`.

**Rationale**: SC-003 says "verified by an automated check rather than review". A public build
artifact containing Semgrep rule files is redistribution under the Semgrep Rules License v1.0 —
a legal boundary, so the failure mode has to be a red job, not a reviewer's memory.

**Corrected during implementation — a `*.yaml` guard is not enough.** The run store keeps the
engines' raw SARIF, and semgrep's SARIF embeds the tool driver's **entire rule catalogue**:
2126 rule descriptions for the 9 rules that fired, 3.9 MB, measured 2026-07-26 at the pinned
SHA. Publishing `out/latest/` wholesale would therefore publish the licensed rules in another
shape while passing a rule-file guard. The workflow now **allow-lists** what it stages —
`findings.jsonl`, `run.json`, `report.md`, `bundle.md`, `sbom.cdx.json` — and the guard rejects
`*.sarif` as well as `*.yaml`/`*.yml`. Whether the store should keep raw SARIF at all, or
strip the driver's rule list down to what fired, is a 001-store question this spec records
rather than settles.

**Also corrected: pinned mode did not work at all.** `--config <checkout root>` makes semgrep
reject the whole run — exit 7, zero files scanned — because the upstream repository ships YAML
that is not a ruleset (`stats/` holds category metadata, `.github/stale.yml` is bot config).
`run.semgrep_configs()` now passes one `--config` per qualifying top-level rule directory (28
at the pinned SHA), where a directory qualifies when every non-fixture YAML under it declares a
top-level `rules:` key. Rule test fixtures (`*.test.yaml`) are tolerated by semgrep and must
not disqualify their directory, or java, ruby and yaml drop out of the ruleset.

**Alternatives rejected**:
- *Trusting the upload path* — one future `path: .` typo is a licence breach.
- *Pruning non-rule files from the checkout after fetching* — mutating a third-party checkout
  to make our invocation work, when the invocation is what is wrong.
- *`actions/cache` on `.ens-rules/`* — GitHub caches are scoped to the repository and not
  public, but a cache of rule content is still a mirror we maintain; a depth-1 fetch is cheap
  enough that the question does not need answering.
